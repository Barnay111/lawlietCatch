# Нагрузочное тестирование BehaviorGuard (MVP)

Инструмент: k6 v2.3.0. Сценарий: `bg-load.js`. Стенд: один ноутбук (Apple Silicon), backend в профиле `dev`
(Spring Boot 4, Hikari по умолчанию), PostgreSQL 17 и Redis 7 в Docker, ML-сервис uvicorn с одним воркером.

**Это не оценка ёмкости продакшена.** Все компоненты делят одну машину, база уже содержит ~4 000 сессий.
Цифры показывают, что пути работают, и выявляют узкие места. Для пилота нужен отдельный стенд.

## Сценарий

| Поток | Что делает | Нагрузка |
|---|---|---|
| sdk_flow | создание сессии, пакет из 40 событий, завершение | 10 VU, 80 с |
| risk_assess | создание сессии, события, оценка риска (с реальным ML) | 4 VU, 80 с |
| dashboard | обзор за 24 часа с токеном администратора | 2 VU, 80 с |

Итого ~54 итерации/с, ~157 HTTP-запросов/с, 12 886 запросов за прогон.

## Найденная проблема и исправление

Перед исправлением обзор дашборда давал **p95 416 мс** и медиану 0.32 с на ~1 250 оценках.
Причина: N+1. Для каждой оценки ленивые связи с сессией и пользователем грузились отдельными запросами.

Исправление: `RiskAssessmentRepository.findForOverview` с `join fetch` сессии и пользователя.
После исправления медиана 0.042 с, p95 76 мс. Результаты обзора (счётчики по уровням) совпадают с прежними.

## Ошибки самого теста (зафиксированы честно)

- Первый прогон: все 320 запросов к обзору вернули 401. Причина в скрипте: заголовки переданы в `http.post`
  без обёртки `headers`, вход администратора не прошёл, токен был `undefined`. Прогон не учитываем.
- Задержки dashboard в первом прогоне (3.7 мс) были быстрыми ошибками, а не работой. Тоже не учитываем.

## Ограничения, которые важно знать

1. Цифры сняты на одной машине вместе с базой и ML. На отдельном стенде они будут другими.
2. Обзор дашборда читает все оценки периода в память. Задержка растёт линейно с числом оценок.
   При ~10 000 оценок за сутки это станет проблемой: нужны агрегирующие запросы в БД или материализованные счётчики.
3. Не проверялись: пиковая нагрузка выше ~55 итераций/с, длительные прогоны (часы), деградация при заполненных логах.
4. Пул соединений Hikari не настраивался, размер 10 по умолчанию. Под нагрузкой выше ожидаемой это следующий кандидат.
5. Событий в батче 40, тогда как лимит сервера 200. Для SDK с большим трафиком стоит измерить батчи по 200.

## Как повторить

```bash
k6 run loadtest/bg-load.js \
  -e BG_SDK_KEY=bg_pk_... -e BG_SERVER_KEY=bg_sk_... \
  -e BG_ADMIN_USER=admin -e BG_ADMIN_PASS=...
```
Ключи берутся из вывода dev-профиля backend. Не коммитьте их.

## Дашборд: агрегаты в базе (этап 1 из плана)

Обзор переведён с загрузки всех оценок периода в память на агрегаты PostgreSQL:
- счётчики по последней оценке каждой сессии: `DISTINCT ON (session_id)` и группировка по уровню;
- почасовой ряд: `GROUP BY` по часу UTC, метка содержит дату;
- таблица последних оценок: `LIMIT` и `join fetch` пользователя.

Замер на 100 000 синтетических оценок (метка `model_version = 'bench'`, после замера удалены):

| Окно | До (загрузка в память) | После (SQL) |
|---|---|---|
| 24 часа | — | медиана 0.033 с |
| 7 дней | медиана 0.22 с | медиана 0.071 с |

Заодно найден и исправлен баг: почасовой ряд склеивал одинаковые часы разных дней (24 столбца вместо 168 за неделю).
Метка теперь `DD.MM HH24:00`. Тест на последнюю оценку каждой сессии добавлен: 48 тестов backend проходят.

## Дашборд на 1 000 000 оценок

Синтетика (`model_version = 'bench'`), после замеров удалена, latest-состояние сессий пересчитано.

| Этап | Обзор, 7 дней (медиана) | Обзор, 24 часа (медиана) |
|---|---|---|
| Агрегаты SQL (DISTINCT ON), без индекса | 0.21 с | — |
| + индекс (organization_id, created_at) INCLUDE (session_id, risk_level) | 0.16 с | — |
| + последний уровень хранится в сессии (V6) | 0.17 с | 0.09 с |

Индекс сам по себе почти не дал выигрыша: узким местом была сортировка DISTINCT ON по 205 тысячам строк.
Хранение последнего уровня в сессии убрало сортировку. Сверка с прямым запросом совпала: 19 812 / 133 620 / 40 002 / 8 130.
Оставшееся время растёт с числом строк в окне. Следующий шаг при объёме в десятки миллионов оценок —
почасовые агрегаты (rollup-таблица), в текущем объёме это не нужно.
